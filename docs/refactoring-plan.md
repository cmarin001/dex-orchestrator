## Patterns and contributor conventions

The current code already uses adapters for model and chain boundaries, composition factories for context-specific implementations, strategies for entry/exit proposals, command receipts for operations, and ordered provider fallback. These address concrete variation. A builder or abstract factory would add indirection without resolving the selected readability issues. A facade, decorator, composite, bridge or proxy would introduce another boundary for logic that already has an owner. A mediator, observer, state machine abstraction, template method or new specification framework would change coordination or obscure ordering in the selected refactors. Use private extraction and named functions for these changes.

Keep runtime schemas at ingress. Model untrusted data as unknown until validation and use narrow typed ports where a current caller needs them. Keep async effect ordering explicit and never swap a strict parser for a tolerant parser during cleanup. Preserve error values, logs, journal append order, integer arithmetic and public defaults. Keep payment/signing capabilities out of intelligence and strategy code. Reuse the existing type checks, import tests, simulation and CI scripts. Introduce a new tool only if an existing gate cannot enforce a concrete invariant.
