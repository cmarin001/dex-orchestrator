# LLM harness tool policy

Approval gate for the harness. This draft uses the original [PR #19](https://github.com/cmarin001/dex-orchestrator/pull/19) inventory as amended by [PR #20](https://github.com/cmarin001/dex-orchestrator/pull/20), which adds the planned internal-health mapping. Every one of the 378 Table 4 names appears once below. The table describes a future model profile, including tools that still await their implementation batch.

Signers and the nine prompt files already lack MCP names in Table 4. Their REST metadata routes stay outside model reach. The rows marked deny are removed before discovery and rejected at the model-facing dispatch boundary. The base operator catalog and the model-facing catalog have separate permissions. The worker and signer execute approved transitions; the model cannot submit raw transactions.

- ALLOW presents only read and reflection capabilities in the default model profile. Diagnose unavailable status or missing metadata accurately and return scoped results.
- ASK tools start hidden. An operator explicitly enables one tool before it enters the approval flow. Bind approval to the one tool and normalized arguments, and independently enforce backend role and recent MFA before dispatch. Refused or expired requests produce no backend call.
- DENY has no approval route or override. Authorization is enforced outside model text.
- Native Hermes forwarding is tested against the pinned server. Fallback C uses a curated Hermes operator surface if raw forwarding fails. The three-hop log test must record each observed hop, with shared correlation and real transport labels. Shared service execution alone does not constitute a REST request.
- Phase 2 will verify the actual Hermes configuration keys and approval behavior for the pinned version before treating them as authorization. Backend enforcement is mandatory even when the Hermes client filters tools.
